# 开发规范规则

## 概述
本文档定义了项目开发过程中必须遵循的文档更新规范，确保技术文档、进度记录和组件说明始终保持最新状态。

## 文档更新规则

### 1. 组件相关开发
**触发条件**：开发和打包微信小程序组件相关的任务

**必须更新的文档**：
- `e:\Project\fsj\merchantDashboard\components\README.md`

**更新内容要求**：
- 新增组件时：添加组件说明文档，包括作用、功能特性、可配置属性、使用场景
- 修改组件时：更新对应组件的功能说明和属性配置
- 删除组件时：移除对应的组件说明
- 更新组件开发规范部分（如果有变化）
- 更新数据绑定和排序规则说明（如果有变化）

**示例场景**：
- 新增一个视频组件 → 在 README.md 中添加视频组件的完整说明
- 修改轮播图组件的属性 → 更新轮播图组件的可配置属性列表
- 调整组件的数据绑定逻辑 → 更新数据绑定部分的说明

---

### 2. 技术路线相关开发
**触发条件**：任务中提到和技术路线相关的内容

**必须更新的文档**：
- `e:\Project\fsj\.cursor\skills\技术路线.mdc`

**更新内容要求**：
- 新增技术方案：在对应模块下添加详细的技术设计说明
- 修改技术方案：更新相关的技术实现细节
- 补充技术细节：完善技术路线中缺失的实现说明
- 更新架构图或流程图（如果有变化）
- 补充代码示例和配置说明

**示例场景**：
- 实现算法推荐功能 → 在技术路线的「算法推荐模式」部分补充实现细节
- 修改打包流程 → 更新「打包流程」章节
- 新增数据绑定规则 → 在「数据绑定与算法推荐」章节添加说明

---

### 3. 需求补充和功能开发
**触发条件**：根据需求有需要补充的内容

**必须更新的文档**：
- `e:\Project\fsj\开发进度.md`

**更新内容要求**：
- 新功能开发：在「待开发功能」章节添加对应的待办项
- 功能完成：将待办项从「待开发功能」移动到「已完成功能」
- 功能改进：在「改进记录」章节添加改进说明
- Bug修复：在「改进记录」章节记录问题和解决方案
- 进度更新：按照最小单元拆分任务，确保每个任务可独立验证

**更新格式要求**：

**新增待办项格式**：
```markdown
### X. 模块名称
- [ ] 具体任务描述
- [ ] 具体任务描述
```

**完成任务格式**：
```markdown
### X. 模块名称
- [x] 具体任务描述
```

**改进记录格式**：
```markdown
- 日期：YYYY-MM-DD
- 模块：模块名称
- 关联条目：勾选项（如：### 1. 算法推荐能力接入）
- 问题描述：具体问题描述
- 改进方案与效果：改进措施和效果说明
```

**示例场景**：
- 开始开发算法推荐 → 在「待开发功能」中添加「算法推荐能力接入」模块
- 完成数据绑定UI → 将对应待办项标记为 `[x]` 并移到「已完成功能」
- 修复底部导航栏样式问题 → 在「改进记录」中添加记录

---

### 4. PRD文档更新
**触发条件**：提出新的产品概念、功能需求、技术方案或发现现有PRD需要补充完善时

**必须更新的文档**：
- `e:\Project\fsj\.docs\AI赋能商家平台 - 产品需求文档(PRD).md`

**更新内容要求**：
- **新增功能/概念**：
  - 在对应章节添加详细的功能描述
  - 补充需求详情、验收标准
  - 更新产品架构或功能模块图
  - 补充技术实现细节

- **功能调整/优化**：
  - 更新对应功能的需求描述
  - 调整验收标准
  - 更新技术方案或架构图

- **新发现/新想法**：
  - 在对应章节补充新概念说明
  - 添加新的功能模块
  - 更新产品定位或目标
  - 补充技术选型或架构调整

- **版本迭代**：
  - 更新版本号和更新日期
  - 在版本规划章节添加新版本内容
  - 调整MVP或后续版本的功能列表

**更新格式要求**：

**新增功能格式**：
```markdown
#### X.X.X 功能名称
**功能描述**：功能简要说明

**需求详情**：
- 需求点1
- 需求点2

**验收标准**：
- 验收点1
- 验收点2
```

**新增概念格式**：
```markdown
### X.X 概念名称
**定义**：概念的定义和说明
**作用**：在产品中的作用
**实现方式**：技术实现方案
```

**版本更新格式**：
```markdown
> 版本：V1.1
> 更新日期：YYYY-MM-DD
```

**示例场景**：
- 提出AI协同开发的新概念 → 在「未来规划」章节添加「AI协同开发」详细说明
- 发现需要新增DIY组件功能 → 在「组件系统」章节添加「DIY组件」完整描述
- 调整产品定位为AI赋能商家平台 → 更新「产品定位」和「产品架构」章节
- 确定MVP版本需要包含的功能 → 在「版本规划」章节明确MVP功能列表

**边开发边摸索原则**：
- 本项目采用边开发边摸索的模式，PRD文档是动态演进的
- 每次提出新概念、新需求时，及时更新PRD文档
- PRD文档应反映当前的产品理解和设计方向
- 随着开发深入，不断补充和完善PRD内容
- 保持PRD文档与实际开发进度的一致性

## 执行流程

### 任务开始前
1. 分析任务类型，确定需要更新的文档列表
2. 查看相关文档的当前状态
3. 理解任务对文档的影响范围

### 任务执行中
1. 按照开发规范进行代码开发
2. 同步更新相关文档内容
3. 确保文档与代码实现保持一致

### 任务完成后
1. 检查所有必须更新的文档是否已完成更新
2. 验证文档内容的准确性和完整性
3. 确保文档格式符合规范要求

---

## 检查清单

### 完成任务前必须确认：
- [ ] 如果涉及组件开发，是否更新了 `components/README.md`？
- [ ] 如果涉及技术路线，是否更新了 `技术路线.mdc`？
- [ ] 如果涉及需求补充，是否更新了 `开发进度.md`？
- [ ] 如果提出新概念、新需求或发现PRD需要补充，是否更新了 `PRD.md`？
- [ ] 所有更新是否准确反映了代码实现或产品理解？
- [ ] 文档格式是否符合规范要求？
- [ ] 是否有遗漏的更新内容？

---

## 注意事项

1. **及时更新**：文档更新应与代码开发同步进行，不要延迟到任务结束
2. **准确性**：确保文档内容与实际代码实现完全一致
3. **完整性**：不要遗漏任何需要更新的文档内容
4. **规范性**：严格按照文档格式要求进行更新
5. **可追溯性**：改进记录应包含足够的细节，便于后续追踪
6. **最小单元**：任务拆分应遵循最小单元原则，确保每个任务可独立验证
